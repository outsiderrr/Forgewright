## 3. 必修（🔴 CRITICAL）

### 3.1 [ARCH] generator/context_assembler.py:654 — `state_paths_read` 没有记录 prompt 实际读到的 state paths

**问题**：`accumulate_scene_context_trace()` 只把 character / location / clock / relation 的 id 放进 `ontology_ids_read`，没有把 prompt 中实际可见的 state paths 写入 `trace.state_paths_read`。例如 `system_time` 明确渲染了 `world.scene_count` / `world.long_rest_count`，`prior_scene_summaries[*].key_state_paths` 也会进 prompt，但这些都不会进入 sidecar；当前 `state_paths_read` 主要靠 `accumulate_written_paths_from_graph()` 在生成后把写入 path 回填。

**为什么是 CRITICAL**：ADR-023 / STAGE_3_TASKS §3.2 明确要求 dep_index 是 context assembly over-approx trace，不是 scene 反查。漏记读依赖会让 T-3.7 本体/状态变更反向 propagate 漏标 stale 场景，直接掏空 C6 的价值。

**修复建议**：
```python
# 当前（只记录实体 id；没有记录 prompt-visible state paths）
def accumulate_scene_context_trace(trace, scene_ctx):
    ...
    for clock in scene_ctx.active_clocks or []:
        clock_id = clock.get("id")
        if isinstance(clock_id, str) and clock_id:
            trace.ontology_ids_read.add(clock_id)
            trace.clock_ids_referenced.add(clock_id)

# 建议：在 context assembly trace 中记录所有进入 prompt 的具体 state path
def accumulate_scene_context_trace(trace, scene_ctx):
    ...
    trace.state_paths_read.update({"world.scene_count", "world.long_rest_count"})

    for summary in scene_ctx.prior_scene_summaries or []:
        for path in summary.key_state_paths:
            if isinstance(path, str) and path:
                trace.state_paths_read.add(path)

    for clock in scene_ctx.active_clocks or []:
        ...
        for effect in clock.get("tick_effects") or []:
            path = effect.get("path") if isinstance(effect, dict) else None
            if isinstance(path, str) and path:
                trace.state_paths_read.add(path)
```

### 3.2 [SCHEMA] generator/generate_scene.py:650 — `scene_history_referenced` 写入的是未裁剪历史，不是 LLM 实际看到的历史

**问题**：`generate_scene()` 已经在 `trace.scene_history_referenced` 里计算了 post-truncation 的历史 scene id，但 `_run_post_success_hooks()` 调 `write_sidecar()` 时传的是完整 `scene_ctx.prior_scene_summaries`。`dep_index_writer.build_sidecar_payload()` 又从这个完整列表生成 `scene_history_referenced`，所以当输入超过 5 条时，sidecar 会记录没有注入 prompt 的旧 scene；同时 `summaries_injected_count` / `summary_source_hashes` 仍只对应裁剪后的 5 条，字段互相矛盾。

**为什么是 CRITICAL**：ADR-024 / SCHEMA_v0.3 §9.5 要求 `scene_history_referenced` 记录注入 prompt 的 prior summaries，对应上限 5 条。当前 sidecar 不是“LLM 实际看过什么”的 trace，违反 ADR-023 的依赖索引语义。

**修复建议**：
```python
# 当前：传入完整 pre-truncation 列表
sidecar_path = write_sidecar(
    scene_path,
    graph,
    trace,
    scene_ctx.prior_scene_summaries,
    scene_ctx.token_metrics,
    ...
)

# 建议：传入与 token_metrics/hash 同一套 post-truncation 列表，或让 writer 直接用 trace.scene_history_referenced
kept_summaries, _ = truncate_prior_scene_summaries(scene_ctx.prior_scene_summaries)
sidecar_path = write_sidecar(
    scene_path,
    graph,
    trace,
    kept_summaries,
    scene_ctx.token_metrics,
    ...
)
```

### 3.3 [ERR] generator/batch_scheduler.py:206 — 无法满足的 DAG 依赖仍会被调度或从结果中消失

**问题**：`plan_layers()` 把 unknown dependencies 从 `effective_deps` 过滤掉，因此 `depends_on_scene_ids=["nonexistent_root"]` 的 scene 会进入 layer 0 并开始生成。cycle 场景则只进入 `plan.cycle_remaining`，`run_batch()` 仅 warning，后续只遍历 `plan.layers`，不会为这些 SceneSpec 生成失败 `SceneOutcome`；最终 success_rate 的分母也不含被跳过的 scene。

**为什么是 CRITICAL**：ADR-026 / F4 的核心是 SceneSpec DAG 拓扑调度，“依赖场景完成前不得开始”。unknown dependency 不能被视为已满足；cycle / invalid spec 也必须体现在 “每 scene status” 的 BatchResult 中，否则 T-3.10 实测可能报告 100% 成功但实际漏生成场景。

**修复建议**：
```python
# 当前：unknown dep 被过滤，scene 仍可运行
unknown = [d for d in s.depends_on_scene_ids if d not in seen_ids]
effective_deps[s.scene_id] = [
    d for d in s.depends_on_scene_ids if d in seen_ids
]

# 建议：real run 对 unknown/cycle 生成失败 outcome 或 fail-fast；至少不要调度这些 scene
if plan.unknown_dependencies:
    outcomes.extend(
        SceneOutcome(
            scene_id=sid,
            success=False,
            layer_idx=-1,
            elapsed_seconds=0.0,
            cost_usd=0.0,
            scene_path=by_id[sid].scene_path,
            failure_reason="unknown_dependency",
            failure_metadata={"missing": missing},
        )
        for sid, missing in plan.unknown_dependencies.items()
    )
```

## 4. 应修（🟡 IMPORTANT）

### 4.1 [SCHEMA] generator/dep_index_writer.py:246 — token metrics 默认值被省略，后续无法区分“未记录”与“记录为 0/none”

**问题**：`build_sidecar_payload()` 只有在 `prompt_token_estimate > 0`、`summaries_injected_count > 0`、`summary_source_hashes` 非空、`truncation_reason != "none"` 时才写入四个 token metrics 字段。测试还在 `test_payload_drops_token_metric_defaults()` 中把这个行为锁住。这样 0 条 summary / 未截断的正常场景在 sidecar 里看起来像“没有运行 token metrics hook”。

**为什么是 IMPORTANT**：ADR-024 与本次 L2 checklist 要求每 scene 把四个 token metrics 字段记录到 dep_index，枚举严格对齐 T-3.2 schema。省略默认值不会违反 JSON Schema，但会削弱阶段 3 末期 token 累积曲线与长对话一致性回归分析。

**修复建议**：
```python
# 当前：默认值不写
if token_metrics.summaries_injected_count > 0:
    payload["summaries_injected_count"] = token_metrics.summaries_injected_count
if token_metrics.truncation_reason and token_metrics.truncation_reason != "none":
    payload["truncation_reason"] = token_metrics.truncation_reason

# 建议：只要 token_metrics 存在，就写完整四字段；schema 已允许 0 / "none"
if token_metrics is not None:
    payload["prompt_token_estimate"] = token_metrics.prompt_token_estimate
    payload["summaries_injected_count"] = token_metrics.summaries_injected_count
    payload["summary_source_hashes"] = list(token_metrics.summary_source_hashes)
    payload["truncation_reason"] = token_metrics.truncation_reason
```
