## 3. 必修（🔴 CRITICAL）

### 3.1 [ERR] /generator/generate_scene.py:168 — `generate_scene()` 没有兜住通用异常，仍会向调用方 raise

**问题**：`generate_scene()` 只捕获了 pre-flight 的 `BudgetExceeded`，但 `provider.estimate_cost()`、`_scene_budget_usd()` 的 env 解析、`build_scene_graph_context()`、`generate_scene_skeleton_first()`、`schema_check.check()`、`validate_graph_mechanical()` 都在顶层 try/except 之外。任一路径抛出 `ValueError` / `ProviderError` / `AssertionError` / validator 内部异常时，调用方会直接收到异常，而不是 `SceneResult(success=False, ...)`。

**为什么是 CRITICAL**：T-2.6 §1 步骤 9 明示“不抛异常给调用方”；本 PR docstring 也承诺 “never raises”。这是主对外函数的错误处理契约，破坏后 batch runner / review CLI 需要额外 try/except 才能安全记录失败。

**修复建议**：
```python
# 当前（多个异常点裸奔）
estimated_cost = estimate_scene_cost(
    npc_count=len(participating_npcs),
    beat_count=len(target_beats),
    expected_node_count=expected_node_count,
    provider=provider,
)
...
inner = generate_scene_skeleton_first(...)
...
schema_issues = schema_check.check(graph)
...
mech_results = dialogue_validator.validate_graph_mechanical(graph, ontology=ontology)

# 建议：按失败层分段兜底，全部返回 SceneResult
try:
    estimated_cost = estimate_scene_cost(...)
    _scene_budget_pre_flight(estimated_cost)
except BudgetExceeded as exc:
    return SceneResult(success=False, failure_reason="budget_exceeded",
                       schema_issues=[f"budget_exceeded: {exc}"])
except Exception as exc:
    _LOG.exception("scene budget pre-flight failed")
    return SceneResult(success=False, failure_reason="provider_error",
                       schema_issues=[f"cost_estimate_failed: {type(exc).__name__}: {exc}"])

try:
    scene_ctx = build_scene_graph_context(...)
    ...
    inner = generate_scene_skeleton_first(...)
except Exception as exc:
    _LOG.exception("scene generation failed")
    return SceneResult(success=False, failure_reason="provider_error",
                       schema_issues=[f"unexpected_exception: {type(exc).__name__}: {exc}"],
                       inner_results=inner_results, total_cost_usd=total_cost)

try:
    schema_issues = schema_check.check(graph)
except Exception as exc:
    return SceneResult(success=False, failure_reason="schema_invalid",
                       schema_issues=[f"schema_check_exception: {type(exc).__name__}: {exc}"],
                       inner_results=inner_results, total_cost_usd=total_cost)

try:
    mech_results = dialogue_validator.validate_graph_mechanical(graph, ontology=ontology)
except Exception as exc:
    return SceneResult(success=False, failure_reason="mechanical_invalid",
                       schema_issues=[f"mechanical_check_exception: {type(exc).__name__}: {exc}"],
                       inner_results=inner_results, total_cost_usd=total_cost)
```

## 4. 应修（🟡 IMPORTANT）

### 4.1 [ERR] /generator/generate_scene.py:200 — schema / mechanical 外层 retry 没有把失败原因回喂给下一次生成

**问题**：外层 loop 在 schema 或 mechanical 失败后只是 `continue`，下一次仍用同一组 `scene_setting / target_beats / participating_npcs / active_clocks / system_time / location_candidates` 调 `generate_scene_skeleton_first()`。`last_schema_issues` 和 `last_mechanical_issues` 只在最终失败返回时使用，没有进入下一轮 prompt；测试里的第二次成功来自 FakeProvider 脚本换了输出，不证明真实 provider 收到了 `OPT_LEN_OVER` 等错误反馈。

**为什么是 IMPORTANT**：T-2.6 §1 步骤 7 和 ADR-020 重试规则写的是“失败回喂 + 重试”，关键测试 #5 也要求“validator 机械预检 issue → 回喂 + 重试”。当前实现实际是随机重采样，真实 LLM 很可能重复同类机械错误，削弱阶段 2 gross pass rate。

**修复建议**：
```python
# 当前
if schema_issues:
    last_schema_issues = [...]
    continue

if node_issues:
    last_mechanical_issues = node_issues
    continue

# 建议方向
# 1. 把上一轮 schema/mechanical issues 渲染成 outer_feedback；
# 2. 通过一个显式参数传给 skeleton/fill prompt，或在 T-2.6 内有清晰的反馈注入点；
# 3. 测试断言第二轮 provider.user_prompts 中包含 OPT_LEN_OVER / schema pointer。
outer_feedback = _render_outer_retry_feedback(last_schema_issues, last_mechanical_issues)
inner = generate_scene_skeleton_first(
    ...,
    outer_feedback=outer_feedback,  # 需要同步扩展 strategy 接口或等价注入点
)
```

### 4.2 [ARCH] /generator/generate_scene.py:264 — 成功路径直接返回 raw graph，没有写入 ADR-019 要求的 `generation_trace.slot_assignments`

**问题**：成功路径把 `inner.graph` 原样放进 `SceneResult(graph=graph)` 返回；当前 T-2.6 新增代码和测试都没有任何 `slot_assignments` 写入或断言。`git grep` 在 T-2.6 相关实现里也没有 `slot_assignments`。这意味着本 PR 产出的节点不会携带 ADR-019 要求的角色槽位 trace。

**为什么是 IMPORTANT**：ADR-019 后果明确写着 `generate_scene`（T-2.6）必须在节点产物里写 `slot_assignments`。schema 已在 T-2.2 做成 optional 以保证兼容，但 generator 主交付物不写 trace 会让后续跨场景同槽一致性和重生成复现缺锚点。

**修复建议**：
```python
# 当前
return SceneResult(
    success=True,
    graph=graph,
    inner_results=inner_results,
    total_cost_usd=total_cost,
)

# 建议：返回前规范化每个节点的 generation_trace
graph = _attach_slot_assignments_trace(graph, scene_ctx)
return SceneResult(success=True, graph=graph, ...)

def _attach_slot_assignments_trace(graph: dict, scene_ctx: SceneGraphContext) -> dict:
    graph = dict(graph)
    nodes = dict(graph.get("nodes") or {})
    for node_id, node in nodes.items():
        node = dict(node)
        trace = dict(node.get("generation_trace") or {})
        trace.setdefault("source", "llm")
        trace.setdefault("generated_at", None)
        trace.setdefault("model_id", None)
        trace.setdefault("prompt_hash", None)
        trace.setdefault("reviewed_by", None)
        trace.setdefault("reviewed_at", None)
        trace.setdefault("slot_assignments", {})  # 当前无抽象槽时也显式记录为空
        node["generation_trace"] = trace
        nodes[node_id] = node
    graph["nodes"] = nodes
    return graph
```
