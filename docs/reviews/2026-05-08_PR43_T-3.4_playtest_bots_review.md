## 3. 必修（🔴 CRITICAL）

### 3.1 [ERR] `generator/playtest/cli.py`:417 — calibration 没有计入 judge 调用，实测成本会系统性偏低

**问题**：`run_calibration()` 只跑 `_run_persona_batch()`，随后明确跳过 judge。这样 `avg_calls_per_path` / `avg_cost_per_path` 只包含 persona decision call，不包含每条 path 后续的 LLM-as-judge call。T-3.4/F9 明确要求 calibration 实测“每决策节点 + judge”的真实 calls/path、tokens/path、seconds/path、cost/path；当前报告会低估至少 1 次 LLM 调用 / path，并把 full batch 的推荐 `max_paths` 算得过大。

**为什么是 CRITICAL**：违反 ADR-022/F9 的 mandatory calibration 口径，也削弱 ADR-012 成本治理；5×20 full batch 会基于错误预算放行。

**修复建议**：
```python
# 当前（问题代码片段）
paths = _run_persona_batch(...)

# Don't judge during calibration — the spec wants calls/path data,
# and the judge call doubles cost. The full batch will judge.
avg_calls = sum(p.llm_calls for p in paths) / n
avg_cost = sum(p.cost_usd for p in paths) / n

# 建议
before_calls = g.total_calls
before_cost = g.total_cost
before_input_tokens = g.total_input_tokens
before_output_tokens = g.total_output_tokens

paths = _run_persona_batch(...)
_judge_paths(
    scene=scene,
    persona_lookup={persona.persona_id: persona},
    paths=paths,
    provider=provider,
    guard=g,
)

avg_calls = (g.total_calls - before_calls) / n
avg_cost = (g.total_cost - before_cost) / n
avg_in = (g.total_input_tokens - before_input_tokens) / n
avg_out = (g.total_output_tokens - before_output_tokens) / n
```

### 3.2 [SAFETY] `generator/playtest/cli.py`:275 — 三重 guard 只记账不检查，且 abort 时会丢掉已完成路径

**问题**：runner 阶段的 observer 只调用 `guard.observe()`，`guard.check()` 要等整个 persona 的 `n_paths` 都跑完后才执行。也就是说 `--max-cost-usd` / `--max-calls` / `--max-wall-clock-min` 可以被一个 persona batch 大幅越过才 abort。更糟的是，如果 `guard.check()` 或 judge 阶段抛出，代码在 `scene_paths.extend(persona_paths)` 之前 `break`，当前 persona 已完成的 paths 不会写入 `worst_paths.jsonl`，不符合“abort batch + log current progress”。

**为什么是 CRITICAL**：违反 ADR-022/F9 的三重 guard 语义；成本上限不能及时止损，同时 abort 产物会漏掉已经花钱得到的路径。

**修复建议**：
```python
# 当前（问题代码片段）
def _observer(cost: float, input_tokens: int, output_tokens: int) -> None:
    guard.observe(cost, input_tokens, output_tokens)

paths = asyncio.run(run_paths_async(...))
return paths

# 建议方向：在 runner 的路径循环边界检查 guard，并保证已完成 paths 先入账
def _observer(cost: float, input_tokens: int, output_tokens: int) -> None:
    guard.observe(cost, input_tokens, output_tokens)

persona_paths = []
try:
    for path in run_paths_iter(...):  # 或让 run_paths_async 支持 per-path callback
        persona_paths.append(path)
        guard.check()
    _judge_paths(...)
except (BudgetExceeded, GuardTripped):
    scene_paths.extend(persona_paths)
    all_paths.extend(persona_paths)
    aborted = True
    ...
```

同时不要在 runner/judge 内吞掉 observer 抛出的 `GuardTripped`；否则把 `guard.check()` 放进 observer 也不会生效。

## 4. 应修（🟡 IMPORTANT）

### 4.1 [ARCH] `generator/playtest/cli.py`:556 — `run_manifest.json` 缺少 F20 要求的 `option_set` / `raw_choice` 复现信息

**问题**：manifest 目前记录了 model、temperature、prompt hash、persona hashes、rubric version 和 guard 统计，但没有记录 ADR-022/F20 要求的 `option_set` / `raw_choice`。`worst_paths.jsonl` 里也只有 `valid_option_ids` 和 reason，不包含当时完整 option 文本集合或 provider 原始 structured response。后续作者或 L2 只能看到“选了哪个 id”，不能复盘“模型面对哪些选项、原始输出是什么”。

**为什么是 IMPORTANT**：这不一定立刻破坏跑批，但会削弱 worst-10% 回放和审计能力；T-3.4 的 manifest 目标就是让后续可重现单 path。

**修复建议**：
```python
# 当前（问题代码片段）
manifest = {
    "model_id": ...,
    "temperature": ...,
    "prompt_template_hash": ...,
    "persona_hashes": ...,
    "judge_rubric_version": ...,
}

# 建议
manifest = {
    "model_id": ...,
    "temperature": ...,
    "prompt_template_hash": ...,
    "persona_hashes": ...,
    "judge_rubric_version": ...,
    "choice_trace": [
        {
            "path_id": path_id,
            "node_id": node_id,
            "option_set": [{"option_id": ..., "text": ..., "target_node_id": ...}],
            "raw_choice": response.raw_text,
        }
    ],
}
```

如担心 manifest 过大，可把 `choice_trace` 写成 `choice_trace.jsonl`，但 manifest 至少要有稳定字段指向该文件。

### 4.2 [ERR] `generator/playtest/runner.py`:509 — path trace 把“离开当前节点的选择”挂到了目标节点上

**问题**：`PathStep` 的契约写的是“node visit + option chosen leaving it”，但实现是在选完 `chosen_id` 后 append 目标节点，并把 `option_id=chosen_id` 塞到目标节点 step。结果 judge prompt 会看到类似 `n_end_a → go_a`，像是 end 节点选择了 `go_a`；同时 `state_after` 在 append 时还没应用目标节点的 `on_enter_effects`，最终 end 节点的 on-enter 状态永远不会出现在 final_state。

**为什么是 IMPORTANT**：`worst_paths.jsonl` 是 F21 的核心 path trace 产物；trace 错位会误导作者和 LLM judge 对因果链的判断，尤其是涉及 on-enter effect 的路径。

**修复建议**：
```python
# 当前（问题代码片段）
_apply_option_effects(state, chosen_opt.get("effects"))
target = chosen_opt.get("target_node_id")
steps.append(PathStep(
    node_id=target,
    option_id=chosen_id,
    state_after=deepcopy(state.as_dict()),
    valid_option_ids=valid_ids,
    reasoning=reasoning,
))
node_id = target
_apply_on_enter(state, nodes[node_id])

# 建议
steps[-1].option_id = chosen_id
steps[-1].valid_option_ids = valid_ids
steps[-1].reasoning = reasoning

_apply_option_effects(state, chosen_opt.get("effects"))
target = chosen_opt.get("target_node_id")
node_id = target
_apply_on_enter(state, nodes[node_id])
steps.append(PathStep(
    node_id=node_id,
    option_id=None,
    state_after=deepcopy(state.as_dict()),
    valid_option_ids=[],
))
```

并补一条回归测试：end step 的 `option_id is None`，且 final `state_after` 包含 end node 的 `on_enter_effects`。
