### 4.1 [ARCH] generator/prompts/scene/REVIEW_PROMPT_AI_JUDGE_SCENE.md:194 — strict pass 覆盖范围自相矛盾，runner 无法确定最终记录数

**问题**：§D 写 `Pass 2（strict）` 只对 pass 1 标为 borderline 的场景重评；§E line 211 也重复“仅对 borderline 场景重评”。但 §G line 232 又要求 `strict pass 记录数 = success=true AND mechanical_pass=true 的行数`，并且 line 198 写最终 recommendation 按 strict 计。非 borderline 场景到底有没有 strict 记录，当前文档给出两个互斥答案。

**为什么是 IMPORTANT**：T-2.8 `scene_ai_judge` runner 会按本 prompt 生成 `scene_ai_judge_log.jsonl`，T-2.12 / T-2.13 又会消费 strict pass 数据；双 pass 是 T-2.9 待落地点，记录数歧义会直接污染 AI_JUDGE_REPORT 的可复现性。

**修复建议**：
```markdown
# 当前（矛盾）
**Pass 2（strict）**：
- 仅对 pass 1 标"需复评"的场景重新评一遍

# §G
- scene_ai_judge_log.jsonl 的 strict pass 记录数 = batch-dir/results.jsonl 里 success=true AND mechanical_pass=true 的行数

# 建议（与阶段 1 strict 全量复评、§G 对齐）
**Pass 2（strict）**：
- 对所有 success=true AND mechanical_pass=true 的场景重新评一遍；borderline 标记仅用于报告边界带与 lenient→strict 改判数。

# §G
- scene_ai_judge_log.jsonl 的 strict pass 记录数 = batch-dir/results.jsonl 里 success=true AND mechanical_pass=true 的行数
- lenient pass 记录数同样覆盖上述全量场景；borderline 场景在报告中单独统计。
```

### 4.2 [ARCH] generator/prompts/scene/REVIEW_PROMPT_AI_JUDGE_SCENE.md:119 — prompt 的 `borderline` 判定与 baseline protocol 的 accept/reject 阈值不一致

**问题**：baseline protocol line 74 定义 advisory 总判定为“场景级 reject 或节点接受率 <70% 则 reject，否则 accept”。但 prompt §B.3 把 accept 提升到 `node_acceptance_rate ≥ 90%` 且场景总分 `≥16`，其余本应按协议 accept 的 70%–89% / 14–15 分区间变成 `borderline`；输出 schema line 175 也新增了 `"borderline"` 枚举。

**为什么是 IMPORTANT**：ADR-020 / STAGE_2_TASKS 要求场景级阈值 `≥14/20` 对齐 70% 口径，AI 判官虽只 advisory，但 T-2.8/T-2.12 报告会统计 advisory accept/reject。若 prompt 和 protocol 阈值不同，同一场景会在协议中是 accept、在日志中是 borderline，后续作者和 runner 都要猜哪一个才是正式口径。

**修复建议**：
```markdown
# 当前
节点级 accept ≥ 90% AND 场景级 accept (无 S*=0 AND 场景总分 ≥ 16)
  → recommendation = "accept"
其余
  → recommendation = "borderline"

# 建议
节点级聚合 (node_acceptance_rate < 70%) OR 场景级 reject (任一 S* = 0 OR 场景总分 < 14)
  → recommendation = "reject"
否则
  → recommendation = "accept"

# 如仍想保留边界带信号，改成附加字段，不改变 recommendation 口径：
"confidence_band": "strong_accept" | "borderline_accept" | "reject"
```

### 4.3 [ARCH] generator/protocols/STAGE_2_BASELINE_PROTOCOL.md:87 — M2 与 M6 都在检查“五命名空间”，失败码边界重叠

**问题**：M2 定义为“所有 effect.path / condition.path 必须落入 ADR-016 五个命名空间之一”；M6 又写“与 M2 同源，检查 path 整体不出现非五命名空间字段”，示例 `npc.foo.bar` 实际已经会被 M2 拦下。这样 T-2.4 实现时同一个非法 path 可能同时报 M2/M6，或者不同实现者随机选择其一，削弱机械失败 top reason 的诊断价值。

**为什么是 IMPORTANT**：ADR-020 明确机械失败口径用于 gross pass rate 诊断；失败码不互斥会让 T-2.12 的 M1–M7 统计失真。用户给的评审重点也特别要求核对 M2 vs M6 是否重叠。

**修复建议**：
```markdown
# 当前
M2 path 前缀：必须落入五个命名空间之一
M6 state path 命名空间合法性：与 M2 同源；检查 path 整体不出现非五命名空间字段

# 建议 A：合并
M2 path 命名空间合法性：检查所有 effect.path / condition.path 的命名空间与整体 path 形态；
M6 删除或改为其他 ADR-020 字面项。

# 建议 B：拆清楚
M2 path 前缀：只检查第一段 namespace 是否为 world/faction/relationship/flag/player。
M6 path 整体形态：在 M2 通过后检查点分段合法性，例如无空段、无尾随点、segment 只含 [a-z0-9_]+、非裸 namespace，并按 namespace 要求最小深度。
```
