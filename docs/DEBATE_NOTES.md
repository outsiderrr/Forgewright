> 本文件是 Forgewright 项目架构决策的"考古层"。
> 它记录了项目启动前经过的四轮对抗性同行评审（adversarial peer review）的关键结论。

## 讨论的起点

作者是一位独立软件工程师，想用 AI 辅助开发一款类博德之门 3 风格的中小型 RPG，并把生成机制剥离为开源框架。最初的问题陈述模糊，导致前两轮辩论部分走偏。核心澄清在第五轮到来（玩家交互模式是**预生成选项式**，不是自由文本输入），该澄清让此前大量技术讨论变得不适用。

本文档按"讨论主题"而非"时间顺序"整理，便于未来查询。

## 主题 1：玩家交互模式 —— 最关键的澄清

### 一度以为的问题

项目最初被讨论为"AI 驱动的实时叙事引擎"，假设玩家可以自由输入文本，LLM 动态生成 NPC 反应。基于这个假设，**整个第四轮辩论（玩家欺诈防御栈）被展开**，包括：

- 五层防御（constrained decoding、claim-verify-commit、环境预言机、世界模型即代码、叙事一致拒绝）
- 双轨异步架构（小模型做意图识别，大模型只负责叙事生成）
- 流式输出与事后校验的矛盾
- KV Cache 污染、延迟预算、ReAct 冗余等工程问题

### 澄清后的事实

玩家实际交互模式是博德之门 3 式的：

- 玩家看到场景描述和 **3–6 个预生成选项**，点击选择
- 所有对白、分支、NPC 反应由**开发期 AI 辅助生成 + 人工主编审阅**完成，是静态内容
- **运行时不调用 LLM**

### 由此推翻的讨论方向

以下方向对本项目**全部不适用**，不要重新提出：

- 运行时 LLM 调用的任何形态
- 玩家欺诈、社会工程攻击、提示词注入的防御
- 流式输出与结构化输出的冲突
- 实时意图识别、双轨异步
- Swain MRU 作为运行时对白校验器
- 运行时的 KV Cache 优化

### 这些讨论的残余价值

第四轮的工作并非全部废弃。以下内容**在开发期**仍然有价值：

- **Precondition 校验（Story2Game 风格）** 从"运行时守门"转为"编译期校验"：AI 生成选项时声明前置条件，生成管线在内容入库前校验前置条件是否在玩家可达路径上被满足
- **世界模型即代码** 作为世界本体的数据结构设计参考
- **Constrained decoding** 用于开发期 AI 生成，确保输出的实体引用在世界本体内

## 主题 2：架构哲学 —— 自上而下 vs 自下而上

### 第二轮辩论的核心分歧

评审者（Gemini）主张**自下而上的 Agent 模拟**：不预设剧情图，让 NPC 有 GOAP 目标，LLM 基于目标生成行为和对白，剧情从 Agent 交互涌现。作者主张**自上而下的状态图约束**：预设剧情节点和合法转移，LLM 在受约束的选项中填充自然语言。

### 结论

**两者都要，分层共存**：

- 宏观剧情走向由状态图约束，保证戏剧张力（plot-centric 骨架）
- NPC 局部反应由 Agent 行为驱动，保证角色可信（character-centric 肌肉）

### 由此明确的硬约束

- 纯 Agent 模拟存在**叙事坍缩问题**（所有 NPC 都做"理性但无聊的事"，没有戏剧性）
- 纯状态图约束存在**NPC 僵化问题**（缺乏潜台词和即兴）
- Façade 的 Drama Manager 概念的存在本身就证明纯 Agent 路线不足

### 对本项目的启示

因为我们最终走**预生成 + 选项式**路线，这个辩论的直接应用减弱了。但其中的一个洞见对生成阶段仍然关键：

> AI 生成一个场景时，应该先用结构化约束（这个场景属于哪个节拍、推什么价值轴）定框架，再让 AI 在框架内填充角色具体反应。

## 主题 3：数据格式 —— 为什么不用 Articy、Ink、Fountain

### 讨论过的候选

| 候选 | 最初的推荐理由 | 否决理由 |
|---|---|---|
| **Articy:Draft X** | 原生支持节点图 + 变量 + 条件分支，Unity/Unreal 导入器开源，被 Disco Elysium 和 Hogwarts Legacy 使用 | **闭源商业软件**。开源框架依赖闭源工具作为数据源等同于在社区门口设立付费门槛，与长期开源目标根本冲突 |
| **Ink（inkle）** | MIT 许可证，被 80 Days、Heaven's Vault 使用，成熟的作者 DSL | LLM 生成和维护 Ink 脚本极其困难——Ink 的 Knots/Stitches/Tunnels 语法复杂，Cursor 这类 AI 工具几乎无法对 .ink 脚本库建立完整的 AST 理解。对 AI 辅助开发流程不友好 |
| **Fountain** | MIT，LLM 友好，token 效率高 | 无游戏元数据（变量、条件、分支标记）。只适合表达线性剧本，无法表达分支图 |
| **Yarn Spinner 新版** | 成熟的游戏对话 DSL | **YSPL 许可证明确禁止把源码用于 AI 训练**，对 AI 辅助商业化工具是红线 |
| **FDX（Final Draft XML）** | 好莱坞事实标准 | 同 Fountain，线性剧本导向，无分支支持 |

### 最终结论

**JSON-native Schema**。数据主权必须在 JSON 这一层。Ink/Fountain 可以作为导入/导出 adapter（可选），但核心数据结构必须是 JSON Schema 直接定义的。

### 为什么这很重要

开源框架的价值来自标准数据格式的开放性。JSON Schema 可以被任何语言、任何工具读写，不需要专门的 parser。一个独立开发者用文本编辑器都能看懂你的内容文件，这是 Ink 做不到的。

## 主题 4：框架定位 —— Parser 还是 Runtime

### 第三轮辩论的关键钩子

评审者的一针见血：作者最初的调研报告是一份"编剧理论参数化说明书（Parser）"，但开源社区真正缺的是"叙事生成运行时引擎（Runtime）"。开源一份 Parser 没人用，每个项目的叙事需求不同，理论参数化很难一刀切复用。开源一套 Runtime 价值极高，这些工程能力是每个项目都需要的。

### 结论

**项目核心价值是生成 Runtime，不是 Parser**。

### 具体含义

- **框架卖点**：上下文管理、状态持久化、LLM 调度、评测回归、错误恢复、版本控制、审阅工具
- **不是卖点**：十七个编剧学派的 JSON 版本、节拍时间轴参数化

### 编剧理论的正确位置

作为**可替换插件**放在最外层。Save the Cat 是一个插件，起承转结是另一个插件，Egri 是第三个。Runtime 对理论选型保持中立。开发者可以启用多个、任选一个、或全部禁用。

## 主题 5：运行时架构 —— GNR 四层（现已部分不适用）

### 辩论过程中构建的 GNR（Generative Narrative Runtime）架构

1. **State & Variable Bus** — JSON 真相之源，LLM 不能直接写
2. **Context Assembler & Pruner** — 分层激活约束，压缩 prompt
3. **LLM Orchestrator & Validator** — LLM 只输出 JSON tag，确定性代码执行
4. **Narrative Grammar Plugins** — 编剧理论插件

### 澄清后的调整

这四层**对生产期仍然完全适用**，但**对运行时不适用**（因为游戏运行时不调用 LLM）。

调整后的映射：

| GNR 原层 | 现在的位置 | 运行时是否需要 |
|---|---|---|
| State & Variable Bus | `/state` 模块，开发期和运行时都用 | 是 |
| Context Assembler | `/generator` 模块，**仅开发期** | 否 |
| LLM Orchestrator & Validator | `/generator` 模块，**仅开发期** | 否 |
| Narrative Grammar Plugins | `/generator/plugins/`，**仅开发期** | 否 |

### 由此明确的"极简运行时"原则

运行时 = 一个 JSON 对话图播放器 + 状态总线读写。不超过 500 行代码。**任何向运行时添加"智能"的提议都应被否决**——智能全部在开发期实现。

## 主题 6：被承认的补充（评审者的贡献）

以下方向由评审者提出，作者接受，进入架构：

### 1. PbtA 阵营时钟（Faction Clocks）

- 来自桌游 Dungeon World / Blades in the Dark
- 独立于玩家进度的**异步状态机**
- 玩家不作为也会推进（时间驱动或派系行为驱动）
- 解决"玩家躺平故事不动"的平淡失败模式
- **在本项目中的位置**：世界本体的一部分，作为场景生成的驱动力之一

### 2. GOAP / HTN 的数据格式

- 状态字典 + 动作数组，可用纯 JSON 表达
- 比叙事 DSL 的开源门槛低得多
- LLM 可以直接读写
- **在本项目中的位置**：NPC 行为层的设计参考（如果需要 NPC 在开发期有"目标感"）

### 3. 东亚叙事结构

- 起承转结（Kishōtenketsu）对**非对抗性场景**的价值
- 西方理论（Egri 对立统一）过度强调二元冲突
- **在本项目中的位置**：插件层的一个选项，作者可以在日常过渡场景启用

### 4. Drama Manager 概念

- 来自 Mateas 的交互式叙事研究
- 宏观张力调控 AI，监控整体紧张度池
- 通过环境和 NPC 派遣调节曲线，不硬规定节点
- **在本项目中的位置**：开发期的一个生成策略——让 AI 按张力曲线安排场景顺序

### 5. 社交模拟器与关系图谱

- 来自 Crusader Kings 类游戏
- 实体关系图谱（Knowledge Graph）约束 LLM
- **在本项目中的位置**：世界本体的角色关系表结构参考

## 主题 7：Egri Premise 的社区风险

### 作者最初的方案

把 Egri Premise（如"野心导致毁灭"）作为整局游戏的全局不变量，所有生成分支都要通过 Premise 校验器。

### 评审者的批评

把特定价值观硬编码进开源框架，等于对框架使用者施加了作者的世界观。社区开发者想做"虚无主义游戏"时，Premise 校验器就成了系统暴政。

### 结论

Premise **是可选的插件级功能**，不是框架核心。开发者可以注入自己的 Premise，也可以完全关闭这一层。核心层对"故事是否应该有统一主题"保持中立。

## 主题 8：评测的分层

### 最初的建议

用 story-bench 做评测。

### 评审者的批评

story-bench 是线性故事评测框架，BG3 风格分支剧情面临**状态空间爆炸**——不仅要验证单条路径的一致性，还要验证玩家跨路径跳跃时整体剧情图的拓扑健康。

### 结论

**评测必须分层**：

1. **第一层：单路径一致性**。用 story-bench 风格工具，验证每条采样路径的节拍、人物、因果合规
2. **第二层：图拓扑健康度**。图论方法，验证节点覆盖率、不可达节点、死锁、关键路径
3. **第三层：玩家模拟（playtest bots）**。生成大量模拟玩家路径，LLM-as-judge 评分，找出最差的百分之十反馈重做

story-bench 只覆盖第一层。第二层和第三层需要本项目自己实现，这是开源框架的市场机会。

## 主题 9：根本未解问题（诚实承认）

以下问题在四轮辩论中**没有获得满意答案**，属于本项目的真实技术风险：

### 1. "谁来写那张图？"

- 人工写几千节点等同于传统 RPG 开发，失去用 AI 的意义
- AI 生成几千节点无法保证没有逻辑死锁
- **当前应对**：小规模项目（几十到一百场景）不会撞上这堵墙。规模化时**可能**需要 JIT 图扩展（人工画骨架 + AI 实时补子图），但这是开放研究问题
- 对本项目：作者手工写骨架节点 + AI 填充子树 + 人工审阅，规模控制在 50-100 场景

### 2. 长对话的一致性

- 模型在长对话中会遗忘早期锚点
- 不是架构能完全解决的问题，属于 LLM 本身的技术局限
- **当前应对**：记忆流机制（Generative Agents 风格）缓解，但不根治

### 3. 选项质量的评测

- 好的选项列表需要差异性、能力真实性、风格一致性、结果透明度等多重约束
- 没有现成自动化评测方法
- **当前应对**：人工审阅 + LLM-as-judge 辅助，不追求完全自动化

## 主题 10：核心赌注（Forgewright 工具一期；2026-05-13 ADR-031 联动首次明文承认）

### 赌注内容

> **Forgewright 工具一期的核心赌注 = "AI 海量预生成 + 人工审阅 = 给玩家伪即兴体验"。**
>
> 如果这个赌注不成立（AI 无法预生成足够丰富的内容覆盖 GM 即兴空间），整个工具一期定位需要重新审视。

### 触发会话

T-3X-0 阅读伴侣会话（2026-05-13；PR #55 merged）—— 作者本人听完 Crimson Letters（CoC 模组）后识别"GM 即兴 = 人类直觉随机抓取一切上下文产出新分支（如试玩示例：霍布豪斯宅邸临场变成黑帮入场点）"——Forgewright 的应对是**预生成 multi-variant**，赌注成立与否决定项目层面成败。

### 赌注的具体含义

- **GM 即兴特征**：人类直觉随机抓取一切上下文产出新分支；模组没写、玩家创造、GM 即兴接住
- **Forgewright 应对**：预生成 multi-variant（每场景 6-10 option 中 3-5 个为非线性入口；每个入口都有完整 dialogue_graph 子树）
- **赌注的押注点**：玩家**主观体验上**感觉"哇这个游戏怎么什么都能做"——但实际上玩家选项有限，只是丰富度足够掩盖"非真即兴"

### 4 档回退路径

| 失败模式 | 回退路径 | 工程代价 | 影响 |
|---|---|---|---|
| **轻度**：AI 预生成 multi-variant 数量不足 | 加强作者人工编写关键路径变种（每场景手写 1-2 个 multi-variant 兜底）| 低（不改架构）| ROADMAP 阶段 4 内容估算 +20-40% 作者时间 |
| **中度**：AI 预生成质量参差（部分 variant 玩家明显感觉假）| 引入"AI 生成 + 作者 ABC 重审"质量门槛（每场景 60-80% 自动接受率作 baseline；不达标重生成）| 中（generator 加 reject-regenerate 循环）| 阶段 3 实测 throughput 降 30-50%；MVP 场景数从 100 退到 30-50 |
| **重度**：玩家明显感觉"选项有限"破坏伪即兴体验 | **scope 砍**——主线场景数大幅缩减（10 场景精品代替 100 场景宽广）；剩余靠"重玩价值"+ "高分支密度"补偿 | 高（重新定义 MVP scope）| ROADMAP 阶段 4 重写；估时 +6-12 月 |
| **致命**：预生成 + 选项式范式根本无法覆盖叙事 RPG 的多样性需求 | **架构重审** — 考虑回到 DEBATE §1 排除的"运行时 LLM"方向（但需重新评估 ADR-002 + 玩家欺诈防御等）；或彻底改 scope 到非叙事 RPG（如纯解谜 / 卡牌 / 战棋）| 极高（项目重定位）| 工具一期不成立；项目层面战略转向 |

### 实测验证赌注的时机

- **阶段 3 T-3.10 实测期**（1 周 ≥ 10 场景）= 赌注的**第一次实证机会**
- **T-3.10 [A]ccept rate ≥ 60% + Wilson 95% CI**（STAGE_3_TASKS v1.0.2 §1）= 轻度失败模式的早期信号
- **阶段 4 MVP 内容期**（50-100 场景；ADR-010 v0.2 弹性区间）= 中度 / 重度失败模式的实证窗口
- **阶段 4 itch.io 免费发布 + 3-5 朋友玩通**（战略校准 v0.1 完成定义档 c/d）= 致命失败模式的最终验证

### 与 ADR-031 的关系

ADR-031（GM 抉择空间结构化方案）是核心赌注的**工程落地体现**——7 种 GM 抉择空间形式（F1-F7）的 6 种由 ADR-031 推荐方案 D 覆盖；F7 即兴的"伪即兴体验"完全依赖本赌注成立。

赌注成败决定 ADR-031 价值：如赌注重度失败，ADR-031 NPC 状态机 + 多 variant 策略需进入 4 档回退路径。

### 与已立 ADR / 既有原则的关系

- **ADR-001** 玩家交互预生成选项式 = 赌注的架构基础
- **ADR-002** 运行时不调用 LLM = 赌注的硬约束（赌注成败不能破此约束）
- **ADR-010 v0.2** MVP 场景数量弹性 10-100 区间 = 赌注 4 档回退路径的 scope 弹性支持
- **战略校准 v0.1** 北极星 = A 完成度 = 赌注的失败/成功最终判定标准
- **§9.1 "谁来写那张图"** = 赌注的具体子问题（AI 生成 vs 人类手写的混合策略）

### 后续监测建议

- T-3.10 实测期每场景 [A] gate 评估时**附记一句"是否感觉伪即兴破绽"**（轻度信号）
- 阶段 4 内容期定期回看本赌注章节，每 20-30 场景做一次"赌注体感评估"
- 如有任一失败模式触发，作者另起 L1 续接会话 + 进 4 档对应回退路径

## 原则总览（面向未来的 Claude）

如果你时间有限，只记住以下八条：

1. **玩家交互是选项式，不是自由文本**。不要提"玩家欺诈"、"实时生成"、"流式对齐"相关方向。
2. **运行时无 LLM**。运行时 = JSON 播放器，极薄。所有 AI 工作在开发期。
3. **数据必须 JSON-native**。不用 Articy、Ink、Fountain 作为数据源。
4. **框架核心是 Runtime，不是 Parser**。编剧理论是插件。
5. **Plot-centric 骨架 + Character-centric 肌肉**。两者共存。
6. **世界本体是真相之源**。LLM 不能直接写。
7. **Schema 先于生成，校验先于执行**。
8. **主题不变量（Premise）是可选插件，不是核心**。开源框架对价值观保持中立。
